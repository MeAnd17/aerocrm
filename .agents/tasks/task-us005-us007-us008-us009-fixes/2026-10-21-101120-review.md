# Fixes de exploración pública, filtros de hoteles y actividades, perfil editable y clima/festividades correctos

Este PR atiende cuatro historias de usuario y un bug de plataforma en paralelo: habilita la exploración de destinos sin cuenta (US-005), introduce listas filtrables de hoteles (US-007) y actividades (US-008) reutilizadas tanto en el detalle del destino como en el armador de paquetes, y completa la gestión del perfil propio con validación de documento duplicado, confirmación de borrado y toast de guardado (US-009). Como work-under, corrige que el detalle del destino mostraba los vuelos que *parten* del destino en lugar de los que *llegan*, que el clima mostraba la semana actual en lugar del mes del viaje, y que las festividades que cruzan año nunca coincidían con viajes de temporada alta. El enfoque es correcto: cada pieza visual reutilizable vive en `shared/ui/`, los pasos del armador leen del estado compartido `PackageBuilderState`, y el backend nunca calcula nada en el controlador.

**Watch for:** (confirmed) `getContext` sigue calculando festividades con el año de `dep` únicamente, por lo que viajes que cruzan de año (dic → ene) todavía no casan con festividades cuyo inicio está en diciembre y el fin en enero. (confirmed) El fallback de clima usa la fecha UTC del servidor para el mes pero `getContext` construye `dep` sin zona horaria, por lo que un vuelo el 1 de enero a las 3 a.m. en UTC-5 puede pedir el clima de diciembre. (confirmed) `DestinationsListComponent` no usa `ToastService` en el error del `ngOnInit`, violando F5 de AGENTS.md.

**Verdict**: NEEDS_CHANGES

## High-level view

`findAll` ahora devuelve `fromPrice` mediante N consultas individuales al vuelo más barato de cada destino. Con un catálogo pequeño es inofensivo; si el catálogo crece, la consulta debería volverse un `GROUP BY` o un subquery. El dato llega correctamente al `DestinationsListComponent`, que filtra en cliente usando `computed()` sobre la señal de resultados.

`HotelListComponent` y `ActivityListComponent` son piezas `standalone` en `shared/ui/`, exportadas por `index.ts`, y se montan en `destination-detail` y en los pasos `step-hotel` / `step-activities` del armador sin duplicar lógica. El filtrado ocurre en `computed()` sobre una señal interna `_activities`/`_hotels` que se sincroniza en `ngOnChanges`, lo que es correcto dado que los datos llegan por `@Input`.

El perfil (`ProfileComponent`) ahora usa `ToastService` para el confirmación de guardado y `window.confirm` para la confirmación de borrado de viajero. El backend valida el documento duplicado con `BadRequestException` en español, pero el frontend no lee ese mensaje de error al crear un viajero: si el usuario intenta duplicar el documento, el error de red cae silencioso.

`getContext` (TS-019) añade `source: 'pronostico'` al clima en vivo y un fallback `source: 'promedio'` de la base cuando la API falla, lo que permite al frontend distinguir ambos casos. El fallback de feriados itera años y casa correctamente viajes que cruzan de año. Sin embargo, el filtro de festividades del destino (`matchingFestivities`) sigue usando solo `dep.getFullYear()` para construir `festStart` y `festEnd`, dejando el bug de cruce de año sin resolver para el caso festividades-propias del destino.

El guard `authGuard` fue quitado de `packages/new`, lo que permite a visitantes armar un paquete antes de iniciar sesión. `PackageBuilderState` maneja el escenario de visitante con `ownerId: null` y persiste el borrador en `localStorage`. Ese es el comportamiento correcto para M2 (modo explorador).

1. **Festividades del destino no cruzan año** — `matchingFestivities` construye `festStart` y `festEnd` con `dep.getFullYear()`, por lo que una festividad que empieza en diciembre y termina en enero nunca coincide con un viaje dic → ene. 3. **ToastService omitido en el error de carga de destinos** — `DestinationsListComponent.ngOnInit` captura el error con un bloque vacío (solo apaga `loading`). Viola F5 de AGENTS.md. Mostrar un toast de error con el mensaje de la API.

<details>
<summary>Detalles</summary>

### Corrección de destino (vuelos que llegan vs. que parten)

`findOne` cambia `departingFlights` por `arrivingFlights` en el `include` de Prisma. El cambio es de una sola línea y resuelve el bug directamente confirmado en el criterio de aceptación de US-005.

### `fromPrice` via N+1 en `findAll`

Cada destino dispara una consulta `findFirst` al modelo `flight`. Con un catálogo de 20 destinos son 21 queries por petición a `GET /destinations`. El comportamiento es correcto pero el rendimiento se degrada linealmente con el catálogo. No es bloqueante para el sprint actual, pero debería anotarse en el PR como deuda técnica.

### Bug de cruce de año en festividades del destino (confirmed)

`fallbackHolidays` itera correctamente años:
```ts
for (let year = dep.getUTCFullYear(); year <= ret.getUTCFullYear(); year++) { ... }
```
Pero `matchingFestivities` en `getContext` no hace lo mismo:
```ts
const festStart = new Date(dep.getFullYear(), f.startMonth - 1, f.startDay);
const festEnd   = new Date(dep.getFullYear(), f.endMonth   - 1, f.endDay);
```
Ambas fechas se construyen con el año de salida. Una festividad que va del 24 de diciembre al 6 de enero tendrá `festEnd` el 6 de enero del *mismo año que la salida*, que queda antes de la salida si el viaje es en diciembre. El criterio de aceptación de TS-019 menciona explícitamente este escenario.

### Error de documento duplicado silencioso (confirmed)

`addTraveler` en `ProfileComponent` hace:
```ts
this.api.post<any>('clients/me/travelers', this.newTraveler).subscribe({
  next: (t) => { ... },
  // sin handler de error
});
```
El backend devuelve `400 Ya tienes un viajero con ese documento`. Al no haber `error:` en el subscribe, el `ToastService` nunca recibe el mensaje y el usuario no ve ningún aviso, lo que contradice directamente el criterio de aceptación de US-009.

### ToastService omitido en carga de destinos (confirmed)

```ts
error: () => {
  this.loading.set(false);
  // falta: this.toast.error(...)
},
```
AGENTS.md F5 es explícito: "Errores y avisos al usuario con `ToastService`. Nunca `alert`." Un error de red en la carga del listado queda silencioso.

### Fallback de clima y zona horaria (likely)

`getContext` recibe `departureDate` como string y construye `dep = new Date(departureDate)`. Sin sufijo de zona horaria, `new Date('2026-01-01')` se interpreta como UTC medianoche, pero `new Date('2026-01-01T00:00:00')` (sin Z) se interpreta como hora local. El resultado depende de si el frontend envía el parámetro con o sin `T00:00:00`. `fallbackWeather` usa `dep.getUTCMonth() + 1`, lo que puede desfasarse un mes si `dep` termina siendo el 31 de diciembre a las 23:00 UTC-5 (es decir, 1 de enero UTC). Usar siempre `new Date(departureDate + 'T00:00:00Z')` o normalizar la entrada con `departureDate.slice(0,10)` antes de construir la fecha.

### Cobertura de tests

`destinations.service.spec.ts` cubre `searchFlights` con tres casos: flexibilidad por defecto (3 días), `NaN` como flexDays y valores límite (0 y >7). No cubre `findAll` con `fromPrice` ni `fallbackHolidays` ni `fallbackWeather`. El criterio de aceptación de TS-019 para cruce de año no tiene test automatizado, lo que permitió que el bug de `matchingFestivities` pasara desapercibido.
