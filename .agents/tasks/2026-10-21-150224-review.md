# Roles, registro con preferencias y retorno de sesión (TS-016 / US-001 / US-002)

Este conjunto de cambios introduce el modelo de roles (ADMIN / CLIENT) en la capa de datos y en el JWT, elimina la maquinaria de permisos granulares heredada, amplía el registro con campos opcionales y la tercera pregunta de preferencias, y resuelve el problema de retorno post-login. La mayor parte de los criterios se cumplen. Tres problemas bloquean la aprobación: un archivo obsoleto de guard con lógica de rol incorrecta que sobrevivió a la refactorización, un botón de avance que no refleja el estado de validación de la contraseña, y un acento en el mensaje de error del `RolesGuard` que no coincide con el criterio.

**Watch for:**
- (confirmed) `frontend/src/app/core/guards/no-auth.guard.ts` no fue eliminado. El archivo redirige siempre a `/home` ignorando el rol; cualquier importación futura del archivo equivocado silenciaría el comportamiento de admin.
- (confirmed) El botón "Continuar →" del paso 1 del registro no queda deshabilitado cuando la contraseña falla la validación de complejidad — `[disabled]` solo cubre la discrepancia entre los dos campos de contraseña. El usuario puede pulsar el botón sin feedback visual hasta que el error aparece.
- (confirmed) `RolesGuard` lanza `'No tienes permiso para realizar esta acción'` (con tilde), pero el criterio especifica `'No tienes permiso para realizar esta accion'` (sin tilde). Rompe comparaciones exactas de string en tests de contrato.

**Verdict**: NEEDS_CHANGES

## High-level view

`UserRole` (ADMIN / CLIENT) llega al schema, al JWT y al objeto `user` retornado en login y registro. El `RolesGuard` reemplaza al `PermissionsGuard` eliminado; no quedan referencias al sistema de permisos heredado en el backend. El seed crea al administrador sin registro `Client` asociado; los clientes de demo se crean por separado.

El registro amplía el paso 1 con `confirmPassword`, `phone`, `nationality` y `dateOfBirth`, y añade la tercera pregunta de gasto en el paso 2 con cuatro opciones. `spendingRange` viaja al backend y se persiste. El fallo está en que el botón "Continuar →" no refleja el error de complejidad de contraseña hasta que el usuario lo pulsa.

El interceptor resuelve la expiración de sesión: graba `sessionExpired` en `sessionStorage` ante cualquier 401 fuera del login, el componente de login lo lee en `ngOnInit` y muestra el aviso. Tras autenticarse, el admin va a `/admin` y el cliente a `/home`. El `noAuthGuard` en `auth.guard.ts` aplica la misma lógica; el archivo `no-auth.guard.ts` en `core/guards/` sobrevive con la versión que siempre redirige a `/home` — el router lo ignora hoy, pero es un riesgo latente.

<details>
<summary>Details</summary>

### Archivo `no-auth.guard.ts` y duplicidad de nombre

`auth.guard.ts` exporta tres guards: `authGuard`, `adminGuard` y `noAuthGuard`. El último redirige a `/admin` o `/home` según el rol del usuario autenticado. `app.routes.ts` importa `noAuthGuard` desde `auth.guard.ts`, así que en tiempo de ejecución el comportamiento es correcto.

El problema es que `core/guards/no-auth.guard.ts` todavía existe y exporta también un `noAuthGuard` que siempre redirige a `/home` sin comprobar el rol. Cualquier desarrollador que añada una ruta nueva y complete el import automático del IDE puede terminar usando el archivo equivocado. El archivo debería haberse eliminado junto con `permissions.guard.ts`.

### Validación de contraseña sin feedback continuo en el registro

En el paso 1, `passwordError` solo se activa cuando `nextStep()` detecta el fallo y asigna el mensaje. No hay binding a `(ngModelChange)` ni al evento `blur` del campo, así que mientras el usuario escribe, el error no aparece. El botón "Continuar →" tiene `[disabled]="!!(form.confirmPassword && form.password !== form.confirmPassword)"` — esta expresión es `false` (botón habilitado) cuando `confirmPassword` está vacío, lo que es razonable. Pero si la contraseña es `abc` y `confirmPassword` coincide con `abc`, el botón queda habilitado aunque la contraseña no cumpla los requisitos. Al pulsar, `nextStep()` activa `passwordError` y no avanza, pero el usuario no tiene señal previa. El criterio exige que el error sea visible antes de hacer submit.

### Mensaje del RolesGuard

La especificación de TS-016 dice: `"rechaza a un cliente con 'No tienes permiso para realizar esta acción'"`. El criterio de aceptación literal pasado al revisor dice `'No tienes permiso para realizar esta accion'` sin tilde. `roles.guard.ts` lanza la versión con tilde. Si la especificación fuente usa tilde y el criterio de verificación omite la tilde por limitación del canal de texto, el string con tilde puede ser la intención correcta. El equipo debe confirmar qué versión es canónica antes de corregirlo — pero mientras haya discrepancia con el criterio de verificación, el ítem queda abierto.
